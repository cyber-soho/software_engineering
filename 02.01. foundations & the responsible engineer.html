Lesson notes What the lesson covers Slides 2–11

Opening Slides 2–3

Good morning, everyone. Last Tuesday you formed your teams, chose a product and wrote a vision card for it. Today we look at two questions. First: once you know what you want to build, how does a software engineer actually work on it? Second: what does a software engineer owe to the people who use, or are affected by, that software? The hour has four parts, and after each part you get a short active break.

Let me start with a question for you. When you receive a programming assignment, what is the first thing you do? Most people open an editor and start typing. For a small exercise, that can work. For a product that other people depend on, it usually fails, because the code solves a problem that nobody defined clearly. Engineering practice exists to prevent that.

The essence of practice Slides 4–5

In 1945, the mathematician George Pólya published a short book called How to Solve It. It describes four steps for solving a problem. Our textbook uses the same four steps to describe the essence of practice in software engineering. Please write them down: understand the problem, plan a solution, carry out the plan, examine the result.

Step one is to understand the problem. You ask four questions. Who has a stake in the solution? What are the unknowns, meaning which data, functions and behaviour are required? Can the problem be divided into smaller problems that are easier to understand? Can the problem be represented as a diagram or a model? In a software project, this step is communication and analysis: you talk with users and write down what they need.

Step two is to plan the solution. Again, questions. Have I seen a similar problem before? Is there an existing solution, component or pattern that I can reuse? Can I define sub-problems, and do I see a solution for each one? Can I describe the solution in a way that leads to an implementation? In a software project, this step is modeling and design.

Step three is to carry out the plan. You build what you designed, and you check your work as you go. Does the code follow the design? Is each part correct? Has each part been reviewed and tested? In a software project, this step is construction, which means coding and testing.

Step four is to examine the result. Can each part of the solution be tested? Does the result produce the data, functions and behaviour that were required? This is testing and quality assurance. Examining the result often reveals a new problem, and when it does, you return to step one. In other words, the four steps repeat: practice is iterative.

These four steps map onto the five framework activities you met last week. Understanding the problem is communication. Planning the solution is modeling, meaning analysis and design models; the project planning you will do in Blocks 3 and 4 organizes the work around it. Carrying out the plan is construction. Examining the result is the testing part of construction, plus the feedback you receive after deployment. Figure 1 in the module shows this mapping and the Block of your project that covers each step.

Seven principles Slides 6–7

Now, principles. A principle is a general rule that guides decisions when no specific procedure tells you what to do. In 1996, David Hooker proposed seven principles for software engineering practice, and our textbook presents them. I want you to know all seven by name.

The first principle is The Reason It All Exists. A software system is worth building only because of the value it gives its users. Before you add a feature, change a requirement or choose a technology, ask one question: does this give a user something of real value? If the answer is no, do not do it.

The second is KISS (Keep It Simple, Stupid). Choose the simplest design that still meets every requirement, and no simpler than that. Simple does not mean quick and careless. A simple design is easier to understand, easier to test and easier to change. It often takes more thought, and several iterations, to reach a simple design than a complicated one.

The third is Maintain the Vision. A project needs one clear idea of what the product is, shared by the whole team. Without it, each person adds parts that do not fit together. Fred Brooks called the result of a clear vision conceptual integrity: a system that looks as if one mind designed it. Your vision card from Block 1 is the start of that vision.

The fourth is What You Produce, Others Will Consume. Someone else will read your specification, use your design, maintain your code or run your tests. So you write every work product for that person, with clear names, clear documents and clear interfaces.

The fifth is Be Open to the Future. A system that stays in use for a long time delivers more value, and its requirements will change during that time. So you design the system so that it can be extended, and you ask “what if” questions. What if we need a second language, a second campus, a different database? You do not build every future feature now. You avoid decisions that would make those features impossible later.

The sixth is Plan Ahead for Reuse. Reusing a component can save a team time and effort, but reuse rarely happens by accident. If a component could be useful elsewhere, you design its interface and its documentation for that purpose from the start.

The seventh is simply Think! When you think a problem through completely before you act, the result is almost always better, and you are more likely to do the work correctly. And when you still make a mistake, you understand it well enough to learn from it.

How do you use these seven principles? Not as a list to recite, but as questions at the moments when you decide something. When someone proposes a feature, ask The Reason It All Exists. When you choose a design, ask KISS (Keep It Simple, Stupid). When a new idea does not fit the vision card, ask Maintain the Vision. When you write a document or a function, ask who will consume it. When you define an interface, ask what may change next month. And before any of that, ask whether you have thought it through.

Chapter 6 of our textbook, which is part of your reading this week, adds more specific principles. Some guide the process: focus on quality at every step, be ready to adapt, build an effective team, manage change, assess risk. Others guide practice: divide and conquer, use abstraction, strive for consistency, build modular software, look for patterns, and remember that someone will maintain the software after you.

A worked example: QueueLess Slides 8–11

Let me show you how the steps and the principles work together on one of your products, QueueLess, the cafeteria pre-order app. The team receives a complaint: “I ordered at noon, I walked to the counter when the app told me to, and I still waited fifteen minutes.”

Step one, understand. The team measures sixteen orders placed between 11:55 and 12:07. The app tells every student “ready in about four minutes”, but the kitchen can finish only one order every two minutes. On average, a student waits almost nine minutes at the counter, and the longest wait is seventeen minutes. Before changing anything, the team also defines success: at least 90 percent of students should wait two minutes or less.

Step two, plan. The team considers four options: tell each student the real ready time, add a machine-learning prediction, open a second counter, or sell a paid priority pass. KISS (Keep It Simple, Stupid) points to the first option, because a simple calculation from the kitchen queue is enough. The paid pass conflicts with The Reason It All Exists, because the product exists to give every student a quick pickup. The team keeps the calculation behind a replaceable component, which respects Be Open to the Future.

Step three, carry out. The app computes each order’s ready time from the kitchen queue and notifies the student when to come. Step four, examine. The average wait at the counter drops to half a minute, and 15 of the 16 students wait two minutes or less. That is 94 percent, so the success criterion is met.

But the team applies principle seven, Think!, and looks further. The total time from ordering to receiving the meal did not improve; it even rose slightly, from about 12.8 to about 13.3 minutes, because students who arrive late add their own delay. The kitchen is still the slowest step. The students now wait somewhere else instead of standing at the counter. That is a new problem, and the cycle starts again at step one. Real-life example QueueLess: the pickup counter wait Slides 8–10

Task
Reduce the time students stand at the QueueLess pickup counter by working through the four steps of practice, and use Hooker’s principles to choose between four possible solutions.
Relation to the lecture
This is the essence of practice (understand → plan → carry out → examine) applied to a real complaint. It also shows principles eliminating options: KISS (Keep It Simple, Stupid) and The Reason It All Exists decide the plan, Be Open to the Future shapes the design, and Think! sends the team back to step one.

A student complains that she waited fifteen minutes at the counter although she came when the app told her to. The team collects the data of one busy period: 16 orders placed between 11:55 and 12:07. The kitchen needs at least 3 minutes per order and can finish one order every 2 minutes (orders are prepared first in, first out: FIFO (First In, First Out)). The app tells everybody “ready in about 4 minutes”.

Success criterion, written before any change: at least 90% of students wait 2 minutes or less at the counter. Before the change, only 3 of 16 students (19%) meet it; the mean wait is 8.8 minutes and the longest is 17 minutes.

Options: (A) tell each student the real ready time computed from the kitchen queue; (B) predict ready times with a machine-learning model; (C) open a second pickup counter; (D) sell a paid priority pass. Option A is kept (KISS (Keep It Simple, Stupid); it serves every user). Option B is rejected for now but the estimator is placed behind a replaceable interface (Be Open to the Future). Option C does not change the kitchen rate, so it does not reduce waiting. Option D is rejected because it conflicts with The Reason It All Exists: quick pickup for every student.

After the change, students arrive at their notified time, between 3 minutes early and 2 minutes late. The mean counter wait falls to 0.5 minutes and 15 of 16 students (94%) wait 2 minutes or less: the criterion is met. The order-to-meal time, however, stays at about 13 minutes, because the kitchen rate did not change. Think! turns this into the next problem to understand.

// tick() executes exactly one step: it resumes the generator program() until its next "yield" statement.
function tick() {
  // On the very first step, create the generator; program() is defined in the demo-specific part of this script.
  if (!RUN.gen) RUN.gen = program();
  // Resume the program; the returned object tells whether the program has reached its end ("done").
  const r = RUN.gen.next();
  // Count the step for the status line, unless the program has just ended.
  if (!r.done) RUN.steps += 1;
  // When the program has ended, stop the timer and mark the run as finished.
  if (r.done) finish();
  // Refresh the status line after every step.
  statusLine();
  // End of tick().
}
// start() begins, or resumes, the automatic execution: one tick every "speed" milliseconds.
function start() {
  // A finished run cannot be resumed; the user must press Restart first.
  if (RUN.done) return;
  // Mark the run as running.
  RUN.running = true;
  // While the demo runs, the main button offers "Pause".
  $('bStart').textContent = '⏸ Pause';
  // Execute one step immediately, so the click has a visible effect at once.
  tick();
  // Schedule the following steps with the delay chosen in the speed selector.
  if (!RUN.done) RUN.timer = setInterval(tick, Number($('speed').value));
  // End of start().
}

// copyText() puts a text on the clipboard; if the browser refuses the modern method, it uses a hidden text area instead.
async function copyText(text, what) {
  // First try the modern Clipboard interface.
  try { await navigator.clipboard.writeText(text); toast(what + ' copied to the clipboard.'); return; } catch (e) { /* use the fallback below */ }
  // Fallback: create a temporary text area.
  const ta = document.createElement('textarea');
  // Put the text to copy into it.
  ta.value = text;
  // Place it outside the visible area so the page does not move.
  ta.style.cssText = 'position:fixed;left:-9999px;top:0';
  // Add it to the page, because only elements on the page can be selected.
  document.body.appendChild(ta);
  // Select its whole content.
  ta.select();
  // Ask the browser to copy the selection; ok is true when the copy worked.
  const ok = document.execCommand('copy');
  // Remove the temporary text area.
  ta.remove();
  // Tell the user whether the copy worked, and what to do if it did not.
  toast(ok ? what + ' copied to the clipboard.' : 'The browser blocked copying: select the text and press Ctrl+C.');
  // End of copyText().
}

What a software myth is Slide 12

Part two: software myths. A software myth is a widely held belief about how software is built that sounds reasonable but is contradicted by evidence and experience. Myths are dangerous because they sound reasonable, so people act on them. Practitioners sort them into three groups: myths held by managers, myths held by customers, and myths held by developers themselves. For each one, I will state the myth and then the reality.

Why do myths survive? Because each one is true under some conditions, and people generalize from those conditions. Adding workers does shorten a job when the job can be divided into independent parts that need no communication. Changing a document is cheap when nothing else depends on it yet. Software projects rarely meet those conditions: the parts depend on each other, and every decision is used by later work. So, for each myth, look for the condition under which it would be true, and then check whether your project meets it.

Management myths Slides 13–15

First management myth: “Our company has a standards manual, so the team already knows how to build software well.” The reality: a standards manual helps only if people know it exists, actually use it, and if it reflects current practice. Many manuals are outdated, incomplete or ignored. The useful question is not “do we have a manual?” but “do we follow a process that works, and do we improve it?”

Second management myth: “When we fall behind, hiring extra programmers will get us back on schedule.” This is the most famous myth, and it has a name. In 1975, Fred Brooks, who had managed IBM (International Business Machines)’s OS/360 (Operating System/360) operating-system project in the 1960s, published The Mythical Man-Month. In it, he stated what we now call Brooks’s law: adding manpower to a late software project makes it later. In 1999, Brooks received the ACM (Association for Computing Machinery) Turing Award for landmark contributions to computer architecture, operating systems and software engineering. The reasons behind his law can be explained one by one.

Reason one is ramp-up time. A new person does not produce useful work on the first day. They must learn the product, the code, the tools and the decisions the team has already made. During that period they produce little, and the experienced members who teach them produce less than before.

Reason two is communication overhead. Every pair of people who work together is a potential communication path. For a team of n people, the number of paths is n multiplied by (n minus one), divided by two: for four people, four times three divided by two, which is six. Four people have six paths. Six people have fifteen. Eight people have twenty-eight. The work does not grow when you add people, but the coordination does.

Reason three is the limited divisibility of tasks. Some tasks cannot be split among more people, because each step depends on the result of the previous one. Assigning more people to a sequential task does not make it shorter. For example, you cannot test a feature before it is built, and you cannot build the report screen before the team has agreed on the data it displays.

Brooks’s law describes what happens in real projects; it is an observation, and it has conditions. If people join early, receive independent tasks, and the project is not yet late, adding them can help. But once a project is already late, the ramp-up time and the communication cost occur when the least time is left.

Third management myth: “Once another company is building it for us, we no longer need to manage the project.” The reality: a team that cannot plan, track and accept its own work will have the same problems when a contractor does the work. The client still owns the requirements, the acceptance tests and the risk.

Customer myths

First customer myth: “We know roughly what we want, so programming can start now and the details can be settled later.” The reality: vague objectives lead to rework. A complete and stable requirements statement is rarely possible at the start, but the team needs a clear description of the functions, the behaviour, the interfaces, the constraints and the validation criteria, and it gets there through continuous communication with the customer. That is why Block 5 is a requirements document and not a paragraph.

Second customer myth: “Changing software later is easy, because code can always be edited.” The reality: the cost of a change depends on when it is made. A change requested while the requirements are being written costs little. The same change requested after design, or after release, forces changes to designs, code, tests and documents that were built on the old requirement. You met this last week as the cost-of-change curve.

Practitioner myths Slide 16

First practitioner myth: “As soon as the program works, the project is finished.” The reality: a large share of the total effort on a software product, often more than half, is spent after its first release, on corrections, adaptations and improvements. We study this as maintenance in November.

Second: “There is no way to judge quality until the program runs.” The reality: one of the most effective quality activities, the technical review, can be applied to requirements and designs before any code exists. Reviews find defects when they are cheapest to fix.

Third: “A running program is the only thing a project needs to deliver.” The reality: the working program is one part of a software configuration that also includes models, documents, plans and tests. Those are what allow other people to maintain and extend the program.

Fourth: “Software engineering only produces extra documents, and extra documents slow the team down.” The reality: software engineering is not about producing documents; it is about producing quality. Better quality means less rework, and less rework means faster delivery. The agile methods you study in Class 4 keep documentation to what is needed when it is needed, but they do not remove it.

Brooks’s law in numbers: ClubLend Slides 17–20

Let us make Brooks’s law concrete with ClubLend, the club equipment-lending app. A ClubLend team of four is in Sprint 2. They have 60 story points of work left and 18 working days before release. Assume that each experienced member completes 0.8 points per day, and that coordination costs the team 0.05 points per day for each communication path. With four people and six paths, the team completes 2.9 points per day, so 60 points take about 20.7 days. The team is almost three days late.

A manager proposes adding two people. In our model, a newcomer needs 10 days of ramp-up, produces nothing during that time, and costs the others 0.4 points per day in mentoring. If the two newcomers join on day 0, the finish stays at about 20.7 days: no gain. If they join on day 10, when the delay becomes visible, the finish moves to about 23.6 days: the project becomes later. What does help? Reducing scope. If the team and the client agree to move 8 points of low-priority stories to the next release, the finish falls to about 17.9 days, inside the deadline.

In Demo 2 you will see this on a burndown chart, a graph of the work remaining, in story points, against the working day. The dashed line is the four-person baseline. The solid line is your scenario. When newcomers join, the solid line becomes flatter for ten days, because the team produces less while it trains them and coordinates more people. The line becomes steeper only after the ramp-up, and by then the deadline may already have passed.

These numbers come from a teaching model, not from measurements, and you can change every one of them in Demo 2. But the pattern is the one Brooks described, and it is the pattern you will see in your own velocity data in December. The professional response to a late project is to report the problem early, re-estimate, and negotiate scope or schedule with the client. Hiding the delay, or adding people without analysis, makes it worse. You will see in Lesson 4 that this is also a duty in the Code of Ethics.

Before the break, one practical request. This week, listen to your own team. If you hear “we will write the requirements later”, “we can add someone if we fall behind” or “we will test at the end”, you have heard a myth. Name it, and replace it with the reality.

Baseline: 4 × 0.8 − 6 × 0.05 = 2.9 points per day → 60 ÷ 2.9 ≈ 20.7 days. The team is about 2.7 days late.

Proposal: add newcomers. Model assumptions: a newcomer needs 10 days of ramp-up with no output, and each newcomer costs 0.4 points per day of mentoring. With 6 people there are 15 paths.

Results: +2 people on day 0 → about 20.7 days (no gain); +4 people on day 0 → about 21.6 days (later); +2 people on day 10 → about 23.6 days (much later); moving 8 low-priority points to release 1.1 → 52 ÷ 2.9 ≈ 17.9 days (on time). The team reports the delay early, shows these numbers to the client and agrees on the scope change.

// Work left at the start, in story points.
const WORK = 60;
// Size of the experienced team at the start.
const TEAM = 4;
// Points completed per productive person per working day (the measured velocity of the team divided by its size).
const P = 0.8;
// Ramp-up: number of working days a newcomer needs before producing at the full rate.
const RAMP = 10;
// Mentoring cost: points per day that the experienced members lose for each newcomer who is still in ramp-up.
const MENTOR = 0.4;
// Coordination cost: points per day that the team loses for each communication path.
const C = 0.05;
// The release date is 18 working days away.
const DEADLINE = 18;
// paths() returns the number of potential communication paths in a team of n people: n(n−1)/2.
const paths = (n) => (n * (n - 1)) / 2;
// f2() writes a number with two decimals, for example 1.65; it is used for the daily output.
const f2 = (x) => x.toFixed(2);
// dayOutput() computes the net output of working day t (t = 0 is the first day) for k newcomers joining after “join” days.
function dayOutput(t, k, join) {
  // The newcomers are part of the team from their joining day onwards.
  const present = t >= join ? k : 0;
  // A newcomer is in ramp-up during the first RAMP days after joining.
  const inRamp = t >= join && t < join + RAMP ? k : 0;
  // Productive people: the experienced four plus the newcomers who have finished their ramp-up.
  const productive = TEAM + present - inRamp;
  // The team size n decides the number of communication paths.
  const n = TEAM + present;
  // Net output = productive × 0.8 − newcomers in ramp-up × 0.4 − paths × 0.05 (the three mechanisms of Brooks’s law).
  const out = productive * P - inRamp * MENTOR - paths(n) * C;
  // Return every value, because the trace prints the whole calculation.
  return { n: n, inRamp: inRamp, productive: productive, out: out };
  // End of dayOutput().
}
// simulate() runs a whole scenario at once (without drawing) and returns the burndown points and the exact finish day.
function simulate(k, join, cut) {
  // Remaining work at the start: the 60 points minus the scope moved to the next release.
  let left = WORK - cut;
  // Each point of the burndown line is a pair [time in days, remaining points].
  const pts = [[0, left]];
  // Advance one working day at a time (60 days is only a safety limit; every allowed scenario finishes much earlier).
  for (let t = 0; t < 60; t++) {
    // Net output of this day.
    const o = dayOutput(t, k, join).out;
    // If this day finishes the work, the finish happens during the day, at time t + remaining ÷ output.
    if (o >= left) { pts.push([t + left / o, 0]); return { pts: pts, finish: t + left / o }; }
    // Otherwise, subtract the day’s output from the remaining work.
    left -= o;
    // Record the remaining work at the end of day t (time t + 1).
    pts.push([t + 1, left]);
    // End of the daily loop.
  }
  // This line is reached only if the work never finishes, which the allowed settings cannot produce.
  return { pts: pts, finish: Infinity };
  // End of simulate().
}

Why people come first Slide 21

Part three is about people, and then about the Code of Ethics. Software is built by people and for people, and most project failures have human causes: unclear communication, poor coordination, and expectations that nobody wrote down.

Chapter 5 of our textbook lists traits of effective software engineers. They take individual responsibility for their work. They are aware of the needs of their team members and of the stakeholders. They are honest about flaws in their own designs, and constructive about flaws in the designs of others. They stay resilient under pressure. They have a strong sense of fairness, they pay attention to detail, and they are pragmatic: they adapt their methods to the situation instead of applying one method everywhere.

How teams are organized Slides 22–23

Teams have a structure, whether or not anyone designed it. Larry Constantine described four organizational paradigms. A closed paradigm follows a classic chain of command; it works well for projects that resemble earlier ones, but it makes new ideas less likely. A random paradigm is loosely organized and relies on each member’s own initiative; it produces new ideas, but it struggles with orderly, repetitive work. An open paradigm combines some of the control of the closed paradigm with the innovation of the random one; members work together, communicate a lot and decide by consensus, which suits complex problems but can be less efficient. A synchronous paradigm relies on a natural division of the problem, so members work on separate pieces and communicate little with each other.

The agile teams you will study in Class 4 are small, self-organizing and cross-functional: the team decides how to do its work, and together it has all the skills needed to deliver. That is close to the open paradigm. Your team charter from Block 1 uses four rotating roles, Coordinator, Scribe, Builder and Tester, and asks everyone to take part in decisions, which is close to an open structure. Rotation matters: everyone learns every part of the work, and no single person becomes the only one who understands the code.

Stakeholders Slides 24–26

Now, stakeholders. A stakeholder is anyone who can affect, or is affected by, the software and its outcome. That includes the users, the client who pays for or sponsors the product, the operators who run it, people who are affected without ever using it, and regulators. The most common beginner mistake is to list only the users.

A simple tool to organize stakeholders is the power–interest grid. You place each stakeholder according to two properties. Power is their ability to change the requirements, the budget or the approval of the project. Interest is how much the outcome affects them. High power and high interest: manage closely. High power and low interest: keep satisfied. Low power and high interest: keep informed. Low power and low interest: monitor.

Take StudyBuddy, the study-partner app. The Learning Centre coordinator sponsors the pilot: high power, high interest, manage closely. Students looking for partners decide by their adoption whether the pilot continues: manage closely as well. Campus IT (Information Technology) runs the servers: high power, low interest, keep satisfied. Students whose names appear in an imported course roster never chose to use the app, but they are affected by it: low power, high interest, keep informed. The university’s privacy office acts as a regulator: high power, keep satisfied. Demo 3 places eight StudyBuddy stakeholders on the grid and produces an interview plan for the two groups to manage closely.

Talking with stakeholders Slides 27–28

Talking with stakeholders is a skill that can be learned. Chapter 6 gives principles for it: listen; prepare before you meet; let one person facilitate; prefer face-to-face conversation; take notes and document decisions; if something is unclear, draw a picture; when you agree, move on; when you cannot agree, record the disagreement and move on; and treat negotiation as a search for an agreement that both sides can accept, not as a contest. In interviews you will use three types of questions. Open questions invite a description, for example “How do you find a study partner today?” Closed questions ask for a specific fact or a yes or no, for example “Have you used a study-partner app before?” Probing questions follow up on an answer to get detail, for example “You said it takes too long; how long, exactly?” You will prepare this mix, two of each, in the Class 5 Studio.

What a code of ethics is Slide 29

Now the Code of Ethics. A code of ethics is a written set of principles that a profession adopts to guide the decisions of its members, especially when their own interests, or their client’s, conflict with the interests of other people. Software engineering has one. In 1999, a joint task force of the ACM (Association for Computing Machinery) and the IEEE (Institute of Electrical and Electronics Engineers) Computer Society published the Software Engineering Code of Ethics and Professional Practice. It has a short version, which you read this week, and a full version with numbered clauses under each principle.

The Code starts with a commitment: software engineers shall commit themselves to making the analysis, specification, design, development, testing and maintenance of software a beneficial and respected profession. Then come eight principles. I will read their names in the order the Code gives them, and I start with the first on purpose.

The eight principles Slides 30–32

One, PUBLIC: act consistently with the public interest. Two, CLIENT AND EMPLOYER: act in the best interests of your client and employer, consistent with the public interest. Three, PRODUCT: ensure that your products and modifications meet the highest professional standards possible. Four, JUDGMENT: maintain integrity and independence in your professional judgment. Five, MANAGEMENT: managers and leaders promote an ethical approach to managing software development and maintenance. Six, PROFESSION: advance the integrity and reputation of the profession, consistent with the public interest. Seven, COLLEAGUES: be fair to and supportive of your colleagues. Eight, SELF: participate in lifelong learning and promote an ethical approach to the practice of the profession.

Notice the words “consistent with the public interest” in principles two and six. The public interest is the safety, health and welfare of the people affected by the software, including people who never use it. When the interest of the client and the interest of the public conflict, the public interest comes first. That is why I read PUBLIC first.

The full version is precise. Clause 1.03 asks you to approve software only if you have a well-founded belief that it is safe, meets its specifications and passes appropriate tests, and that it does not diminish quality of life or privacy, or harm the environment. Clause 3.10 asks for adequate testing, debugging and review. Clause 6.07 asks you to be accurate about the characteristics of your software and to avoid false claims. Clause 2.06 asks you to report promptly to your client or employer when a project is likely to fail or to cost too much. The late ClubLend project from Lesson 2 is exactly that situation.

Professional judgment underlies all of these clauses: your technical conclusions must not change because someone is pressuring you. Writing “all tests pass” because the release is on Friday is a failure of judgment, even if nobody is harmed that week.

    yield;

    for (let k = 0; k < 8; k++) {
      // The evaluation and its reason.
      const ev = o.ev[k];
      // Count violations and tensions.
      if (ev[0] === 'violation') v += 1; else if (ev[0] === 'tension') t += 1;

    }

Step-by-step: what happens when you press ▶ Start

  1. Press ▶ Start. The wheel shows the eight principles in the Code’s order, PUBLIC at the top. The four options are listed on the scoreboard.
  2. Option A is evaluated principle by principle, starting with PUBLIC. Each segment turns teal (✔ consistent), amber (~ tension) or rust (✘ violation), and the trace prints the clause that justifies it.
  3. At the first ✘ the scoreboard marks the option “eliminated”, but the demo continues through all eight principles so that you see the complete picture.
  4. Options B, C and D follow. The scoreboard counts violations and tensions for each option.
  5. The decision rule is applied: options with any violation are eliminated; among the others, the option with the fewest tensions is recommended and the second one is presented as the alternative.
  6. The demo prints an ethics decision record (context, options, evaluation, decision, who decides, follow-up) that you can copy with ⎘ Copy trace.
  7. Pause on any segment to debate the evaluation; if your class disagrees, that disagreement is itself the discussion the Code asks for.

Lesson notes What the lesson covers Slides 38–48

Five dimensions Slide 38

Last part: social responsibility, or what happens when software hurts people. Software now controls medical devices, aircraft, bank accounts and access to public services. When it fails, the result is not only an inconvenience: people can be injured, their private information can be exposed, they can be treated unfairly, they can be excluded, and resources can be wasted. Engineers study failures so that they are not repeated. We will look at five dimensions of responsibility: safety, privacy, fairness, accessibility and sustainability.

Safety Slides 39–40

A safety-critical system is a system whose failure can cause death, serious injury, or major damage to property or the environment. One of the best-documented software cases is the Therac-25, a radiation therapy machine built by AECL (Atomic Energy of Canada Limited). Between 1985 and 1987, six known accidents occurred in which patients received massive radiation overdoses, and some of these patients died. The investigation by Nancy Leveson and Clark Turner, published in 1993, found causes that acted together. Earlier models had hardware interlocks, which are physical mechanisms that stop the machine in an unsafe state; the Therac-25 relied on software alone. The software contained a race condition, a defect in which the result depends on the timing or the order of events: when an operator edited the treatment data quickly, the machine could be set up in an inconsistent state. Error messages such as “Malfunction 54” gave operators no useful information, and operators learned to resume treatment after them. And when the first accidents were reported, the manufacturer did not accept that the machine could be the cause. The lessons: software must not be the only protection against a hazard, error messages must say what happened, and reports of harm must be investigated, not dismissed.

The second case is Ariane 5. On 4 June 1996, on its first flight, the ESA (European Space Agency) launcher left its course and was destroyed about 40 seconds after the start of the flight sequence. The inquiry board found specification and design errors in the software of the inertial reference system. Software reused from Ariane 4 converted a 64-bit floating-point value into a 16-bit integer. On Ariane 5’s faster trajectory the value was too large, the conversion failed, and the backup unit, which ran the same software, failed in the same way. The failing function was not even needed after lift-off. The lessons: reused software must be verified again against the requirements of the new system, and a backup that runs identical software does not protect against a software error.

The third case is the Boeing 737 MAX. Two aircraft crashed: Lion Air Flight 610 on October 29, 2018, and Ethiopian Airlines Flight 302 on March 10, 2019. In total, 346 people died. In both accidents a flight-control function, the MCAS (Maneuvering Characteristics Augmentation System), repeatedly pushed the nose of the aircraft down after it received an erroneous reading from a single angle-of-attack sensor. In September 2019, the NTSB (National Transportation Safety Board) found that the safety assessment had assumed pilots would recognize and respond to an unintended activation quickly, and that the crews’ actual responses did not match those assumptions, in part because many alerts appeared at the same time. The lessons: an assumption about how humans will react must be validated like any requirement; and one sensor feeding a function that can move the flight controls is a single point of failure.

Privacy Slide 41

Privacy is a person’s right to control information about themselves. Canadian law protects it. PIPEDA (Personal Information Protection and Electronic Documents Act) applies to many private-sector organizations in Canada, and Québec has its own private-sector law, strengthened in 2021 by the law known as Law 25. In 2019, Desjardins disclosed that an employee had copied personal information from shared drives onto USB (Universal Serial Bus) keys over about 26 months. In December 2020, the OPC (Office of the Privacy Commissioner of Canada), investigating jointly with Québec’s CAI (Commission d’accès à l’information du Québec), reported that close to 9.7 million people were affected, and found that Desjardins had not put adequate safeguards in place to control access to, and transfer of, personal information. The engineering answer is privacy by design: build privacy protections into the system from the start. Collect only the data you need, restrict who can see it, protect it, and delete it when it is no longer needed.

Notice two things about this case. First, the person who copied the data was an employee with legitimate access, so protection from outside attackers was not enough; privacy also depends on who inside the organization can see what. Second, the investigators found that some personal information had been kept far longer than it was needed, without a completed retention schedule. Every record you keep is a record that can leak, which is why your Block 2 privacy note asks how long you keep each piece of data.

Fairness Slide 42

Fairness means that the software does not treat groups of people unequally without a justified reason. Software that makes or supports decisions about people can be unfair even when nobody intended it. Joy Buolamwini, then a researcher at the MIT (Massachusetts Institute of Technology) Media Lab, showed that some face-analysis systems performed worse on darker-skinned faces, and connected the problem to training data in which those faces were under-represented. The Government of Canada requires an Algorithmic Impact Assessment before its institutions use an automated decision system, under the TBS (Treasury Board of Canada Secretariat) Directive on Automated Decision-Making. For your project, fairness means three things: know whom your data represents, test the system with different groups of users, and publish the rules the system applies.

Accessibility Slide 43

Accessibility means that people with disabilities can perceive, understand, navigate and interact with the software. The international reference is WCAG (Web Content Accessibility Guidelines), published by the W3C (World Wide Web Consortium); the current version is 2.2. Its four principles say that content must be perceivable, operable, understandable and robust, and it defines three conformance levels: A, AA and AAA. In Canada, the Accessible Canada Act of 2019 aims to realize a Canada without barriers by January 1, 2040, and information and communication technologies are one of its priority areas. The Act applies to organizations under federal jurisdiction, so it does not govern a university app directly, but it shows the direction the country has chosen, and WCAG (Web Content Accessibility Guidelines) remains the reference for your own product. Accessibility is a requirement like any other: you specify it, you design for it, and you test it.

What does that mean in practice? A blind user navigates with a screen reader, software that reads the interface aloud, so every image and every button needs a text label. A user who cannot use a mouse needs every function to work from the keyboard. A deaf user needs captions for video. A user with low vision needs sufficient contrast between text and background. None of these requirements is unusual, and each one can be checked with a test case.

Sustainability Slide 44

Sustainability in software means reducing the energy the software uses and the carbon emissions associated with it, on users’ devices and in data centres. The Green Software Foundation, a non-profit under the Linux Foundation, publishes practices and a metric called SCI (Software Carbon Intensity). For a student project, sustainability means small, measurable choices: do not ask a server for updates every second when a notification will do, do not collect location continuously when you need it once, and compress images before you upload them.

From cases to requirements: SafeCampus Slide 45

Let us apply the five dimensions to SafeCampus, the hazard-reporting app. The team keeps a harms register: for each possible harm, it estimates the likelihood and the severity on a scale from 1 to 5 and multiplies them to get a risk score from 1 to 25. An urgent report that nobody reads overnight: likelihood 3, severity 5, risk 15, which is high. The mitigation: send urgent reports to campus security immediately and show the emergency number on the form, so the app is never the only path to help, which is the Therac-25 lesson. The residual risk is 5. A leak of an anonymous reporter’s identity: likelihood 3, severity 4, risk 12. The mitigation: only the safety officer can see the identity, the form collects the minimum fields, and reports are deleted twelve months after they are resolved. That is privacy by design, and the residual risk is 4. Demo 5 moves five harms, one per dimension, from their risk before mitigation to their risk after mitigation on a five-by-five matrix. Your Block 2 table needs at least five rows of your own, with the columns the schedule asks for: harm, who is affected, likelihood, mitigation and principle; you may add severity and risk as in this model.

Closing Slides 46–48

To close: in each case today, people knew, or could have known, that something was wrong before the harm occurred. The professional response is to report what you know and to design the system so that the harm cannot happen. That is what LO5 (Learning Outcome 5) asks of you: to recognize the professional, ethical and social responsibility of a software engineer. Each of these failures also led to standards, laws and review practices, and you can apply them from your first Block.

Real-life example SafeCampus: a harms register across the five dimensions Slides 45, 47

Task
Build a harms register for SafeCampus: one harm per dimension (safety, privacy, fairness, accessibility, sustainability), each with likelihood, severity, risk = likelihood × severity, a mitigation, and the risk that remains after the mitigation.
Relation to the lecture
Turns the five dimensions and the lessons of the cases (Therac-25, Desjardins, algorithmic fairness, WCAG (Web Content Accessibility Guidelines), green software) into concrete requirements, which is what Block 2 asks for your own product.

SafeCampus lets anyone report a hazard or an incident on campus, optionally anonymously, and follow its status. Scales: likelihood and severity from 1 (very low) to 5 (very high). Risk levels: 1–7 low, 8–14 medium, 15–25 high.

Safety — an urgent report is submitted at night and nobody reads it until morning: likelihood 3 × severity 5 = 15 (high). Mitigation: urgent reports are sent to campus security immediately, and the emergency number is shown on the form. Residual: likelihood 1 × severity 5 = 5.

Privacy — the identity of an anonymous reporter, or of bystanders named in a report, leaks: likelihood 3 × severity 4 = 12 (medium). Mitigation: role-based access (only the safety officer sees the identity), minimum fields, deletion 12 months after resolution. Residual: likelihood 1 × severity 4 = 4.

Fairness — triage ranks reports by the “importance” of the building, so residences wait longer than offices: likelihood 3 × severity 3 = 9. Mitigation: triage by category and time only, the rule is published, and response times are checked every month by building type. Residual: likelihood 1 × severity 3 = 3.

Accessibility — the location can be given only by tapping a map, which a screen-reader user cannot do: likelihood 4 × severity 4 = 16 (high). Mitigation: WCAG (Web Content Accessibility Guidelines) 2.2 level AA as a requirement, a text alternative for the location, and a screen-reader scenario in the acceptance tests. Residual: likelihood 1 × severity 4 = 4.

Sustainability — the app reads the phone’s location every minute in the background: likelihood 4 × severity 2 = 8. Mitigation: read the location only when a report is submitted, and compress photos before upload. Residual: likelihood 1 × severity 2 = 2.

// log() appends one numbered line to the trace window; "kind" selects its colour: info, step, calc, ok, warn or bad.

  // End of log(): the line is stored, displayed and scrolled into view.

// statusLine() describes the current state of the run (ready, running, paused or finished) together with the step number.
function statusLine() {

}
// tick() executes exactly one step: it resumes the generator program() until its next "yield" statement.
function tick() {
  // On the very first step, create the generator; program() is defined in the demo-specific part of this script.
  if (!RUN.gen) RUN.gen = program();
  // Resume the program; the returned object tells whether the program has reached its end ("done").
  const r = RUN.gen.next();
  // Count the step for the status line, unless the program has just ended.
  if (!r.done) RUN.steps += 1;
  // When the program has ended, stop the timer and mark the run as finished.
  if (r.done) finish();
  // Refresh the status line after every step.
  statusLine();
  // End of tick().
}
// start() begins, or resumes, the automatic execution: one tick every "speed" milliseconds.
function start() {
  // A finished run cannot be resumed; the user must press Restart first.
  if (RUN.done) return;
  // Mark the run as running.
  RUN.running = true;
  // While the demo runs, the main button offers "Pause".
  $('bStart').textContent = '⏸ Pause';
  // Execute one step immediately, so the click has a visible effect at once.
  tick();
  // Schedule the following steps with the delay chosen in the speed selector.
  if (!RUN.done) RUN.timer = setInterval(tick, Number($('speed').value));
  // End of start().
}
// pause() stops the timer but keeps the generator exactly where it is, so that start() continues from the same step.
function pause() {
  // Stop the automatic steps.
  clearInterval(RUN.timer);
  // Remember that the run is paused.
  RUN.running = false;
  // The main button offers "Start" again (which will resume the run).
  $('bStart').textContent = '▶ Start';
  // Explain the paused state in the status line.
  statusLine();
  // End of pause().
}
// finish() is called by tick() when the program has no more steps.
function finish() {
  // Stop the timer.
  clearInterval(RUN.timer);
  // Record that the run is complete.
  RUN.done = true;
  // Record that nothing is running any more.
  RUN.running = false;
  // Show "Start" on the main button; it does nothing until Restart is pressed.
  $('bStart').textContent = '▶ Start';
  // End of finish().
}

function restart() {

  clearInterval(RUN.timer);
  // Put the execution state back to its initial values.

  TRACE.length = 0;
  // Empty the trace window on the page.

  // Show "Start" on the main button.
  $('bStart').textContent = '▶ Start';
  // reset() is defined in the demo-specific part: it redraws the visualization in its initial state.

  // Show the "Ready" message.
  statusLine();
  // End of restart().
}

// getSource() returns the source code of this demo, using the best method available where the file is running.
async function getSource() {
  // Case 1: inside the lecture module the demo lives in a frame whose "srcdoc" attribute holds the exact source text.
  try { if (window.frameElement && window.frameElement.hasAttribute('srcdoc')) return window.frameElement.getAttribute('srcdoc'); } catch (e) { /* some browsers refuse this access; cases 2 and 3 still work */ }

  // Case 3: opened from disk, where browsers do not let a page read its own file: return the snapshot taken at load time.
  return SNAPSHOT;
  // End of getSource().
}
// copyText() puts a text on the clipboard; if the browser refuses the modern method, it uses a hidden text area instead.
async function copyText(text, what) {
  // First try the modern Clipboard interface.
  try { await navigator.clipboard.writeText(text); toast(what + ' copied to the clipboard.'); return; } catch (e) { /* use the fallback below */ }
  // Fallback: create a temporary text area.
  const ta = document.createElement('textarea');
  // Put the text to copy into it.
  ta.value = text;
  // Place it outside the visible area so the page does not move.
  ta.style.cssText = 'position:fixed;left:-9999px;top:0';
  // Add it to the page, because only elements on the page can be selected.
  document.body.appendChild(ta);
  // Select its whole content.
  ta.select();
  // Ask the browser to copy the selection; ok is true when the copy worked.
  const ok = document.execCommand('copy');
  // Remove the temporary text area.
  ta.remove();
  // Tell the user whether the copy worked, and what to do if it did not.
  toast(ok ? what + ' copied to the clipboard.' : 'The browser blocked copying: select the text and press Ctrl+C.');
  // End of copyText().
}

// svg() creates an SVG element with a tag name and attributes, appends it to a parent, and returns it so it can be changed later.
function svg(parent, tag, attrs, text) {

  // Attach the element to its parent so that it is drawn.
  parent.appendChild(el);
  // Return the element to the caller.
  return el;

// level() classifies a risk score: 1–7 low, 8–14 medium, 15–25 high.
const level = (r) => (r <= 7 ? 'low' : r <= 14 ? 'medium' : 'high');
// Geometry of the matrix in its 520 × 450 drawing: plotting area of 5 × 5 cells.
const M = { x: 80, y: 16, w: 400, h: 360 };
// Width of one cell (likelihood axis).
const CW = M.w / 5;
// Height of one cell (severity axis).
const CHt = M.h / 5;
// Horizontal offset of each harm inside a cell, so that two harms in the same cell do not hide each other.
const OFF = [-24, -12, 0, 12, 24];
// Vertical offset of each harm inside a cell, so that the arrows of harms in the same row do not cross each other’s dots.

const cy = (S, k) => M.y + (5 - S + 0.5) * CHt + (k === undefined ? 0 : OFFY[k]);
// drawMatrix() erases the drawing and draws the 25 cells coloured by zone, their scores and the axes.
function drawMatrix() {

  const g = $('mx');
  // Erase the previous drawing.
  clear(g);
  // A defs element stores the arrow head used by the mitigation arrows.
  const d = svg(g, 'defs', {});
  // The marker element describes the arrow head.
  const mk = svg(d, 'marker', { id: 'ah5', viewBox: '0 0 10 10', refX: 9, refY: 5, markerWidth: 6, markerHeight: 6, orient: 'auto' });
  // The arrow head is a small dark triangle.

  for (let L = 1; L <= 5; L++) for (let S = 1; S <= 5; S++) { const r = L * S; svg(g, 'rect', { x: M.x + (L - 1) * CW, y: M.y + (5 - S) * CHt, width: CW, height: CHt, fill: r <= 7 ? // program() is the demo itself, written as a generator: every “yield” ends one step, and Pause stops between two steps.
function* program() {
  // State the method.
  log('HARMS REGISTER — for each harm: risk = likelihood × severity (each from 1 to 5); levels: 1–7 low, 8–14 medium, 15–25 high. Then a mitigation, and the residual risk.', 'step');
  // End of this step.
  yield;
  // Running totals of the risk before and after mitigation.
  let before = 0, after = 0;
  // Process the five harms (four steps each).
  for (let k = 0; k < HARMS.length; k++) {
    // The harm being processed.
    const h = HARMS[k];
    // Inherent risk score.
    const r = h.L * h.S;
    // Add it to the total before mitigation.
    before += r;
    // Step a: place the rust dot at the inherent position.
    dot(k, h.L, h.S, false);
    // Show the harm in the state table.
    setCell('s-h', (k + 1) + '. ' + h.harm + ' (' + h.dim.toLowerCase() + ')');
    // Show the inherent risk.
    setCell('s-in', h.L + ' × ' + h.S + ' = ' + r + ' → ' + level(r));
    // Clear the cells that the next steps fill.
    ['s-mit', 's-res'].forEach((id) => setCell(id, '…'));
    // Write the harm and its score.
    log((k + 1) + '. ' + h.dim.toUpperCase() + ' — ' + h.harm + '. Risk = ' + h.L + ' × ' + h.S + ' = ' + r + ' → ' + level(r).toUpperCase() + '.', level(r) === 'high' ? 'bad' : level(r) === 'medium' ? 'warn' : 'info');
    // End of step a.
    yield;
    // Step b: the mitigation and the lesson it applies.
    setCell('s-mit', h.mit);
    // Write the mitigation.
    log('   Mitigation: ' + h.mit + '. Lesson applied: ' + h.lesson + '.', 'calc');
    // End of step b.
    yield;
    // Step c: the residual risk after mitigation.
    const rr = h.rL * h.rS;
    // Add it to the total after mitigation.
    after += rr;
    // Draw the arrow from the inherent to the residual position.
    arrow(k);
    // Draw the teal dot at the residual position.
    dot(k, h.rL, h.rS, true);
    // Show the residual risk.
    setCell('s-res', h.rL + ' × ' + h.rS + ' = ' + rr + ' → ' + level(rr));
    // Write the residual risk. The likelihood falls; the severity stays, because the mitigation prevents the harm but does not make it less serious.
    log('   Residual risk = ' + h.rL + ' × ' + h.rS + ' = ' + rr + ' → ' + level(rr).toUpperCase() + ' (the mitigation lowers the likelihood; the severity of the harm, if it happened, is unchanged).', 'ok');
    // End of step c.
    yield;
    // Step d: the principle of the Code that this mitigation protects, and the register row.
    const tr = document.createElement('tr');
    // Two empty cells, filled with plain text below.
    tr.innerHTML = '<td></td><td></td>';
    // First cell: the number of the harm.
    tr.cells[0].textContent = String(k + 1);
    // Second cell: dimension · harm · inherent → residual · principle.
    tr.cells[1].textContent = h.dim + ' · ' + h.harm + ' · ' + r + ' (' + level(r) + ') → ' + rr + ' (' + level(rr) + ') · ' + h.pr;
    // Add the row to the register.
    $('regBody').appendChild(tr);
    // Write the principle in the trace.
    log('   Principle of the Code protected: ' + h.pr + '.', 'info');
    // Show the running totals.
    setCell('s-tot', before + ' → ' + after);
    // End of step d.
    yield;
    // End of the loop over the harms.
